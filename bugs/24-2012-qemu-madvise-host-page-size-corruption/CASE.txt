END-USER FAILURE: QEMU zero-page optimization discards neighboring guest bytes if host page is larger
CORE FAILURE, NOT AN ERROR-RETURN EXERCISE:
madvise(MADV_DONTNEED) acts on an entire HOST page, even when QEMU requests a shorter guest-target page; QEMU's one-page zero optimization discards adjacent guest data on migration target.
CALL / DATA / STATE PATH:
incoming migration zero guest 4K chunk -> ram_load sees zero -> qemu_madvise length=TARGET_PAGE_SIZE 4K -> host backing page 64K discarded -> adjacent guest subpages lose data
REPRODUCTION PROCEDURE AND REQUIRED RESOURCES:
Requires different host and target page sizes, such as 64K POWER host backing for 4K guest target; use isolated historical POWER guest or emulated environment capable of reproducing host-page semantics. Correct size mismatch must be proven before attempting. Not a laptop Ryzen KVM reproducer.
FAILURE SIGNAL AND CONTROL:
Adjacent data corruption after incoming migration; patch suppresses madvise if getpagesize()>TARGET_PAGE_SIZE.
MANUAL INPUT AND QUESTION:
CONSTRUCTED: host page 65536B, target page 4096B, one discard covers 65536/4096=16 guest pages. How many neighboring pages can be destroyed by one bad hint?
