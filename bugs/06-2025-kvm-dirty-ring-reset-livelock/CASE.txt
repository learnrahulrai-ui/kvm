B06 | KVM dirty-ring reset can loop indefinitely when userspace re-marks ring
PUBLIC ORIGIN YEAR: 2025
EVIDENCE STATUS: CONFIRMED_PATCH_CONTAINS_MINIMAL_CONCURRENT_REPRO
CAN TRY ON SECOND LAPTOP: GOOD_NESTED_KVM_GUEST
LOCAL REPRODUCED: NO_REPRO_RUN
CORE FAILURE, NOT AN ERROR-RETURN EXERCISE:
Kernel harvested entries without a strict processing bound, so producer can keep replenishing the same work while reset loops; ioctl fails to make finite progress.
OBSERVED OPERATION THAT MATTERS:
One process repeatedly invokes KVM_RESET_DIRTY_RINGS while another process repeatedly resets KVM_DIRTY_GFN_F_RESET flags in the MAP_SHARED dirty ring.
FUNCTION-TO-FUNCTION REASONING PATH:
mmap vCPU dirty ring -> process A KVM_RESET_DIRTY_RINGS -> process B rewrites entry.flags=KVM_DIRTY_GFN_F_RESET -> kernel harvest sees more -> A cannot leave ioctl

FIX OR UNCERTAINTY: 2025 v3 series bounds harvest at INT_MAX, checks signals, conditionally reschedules
