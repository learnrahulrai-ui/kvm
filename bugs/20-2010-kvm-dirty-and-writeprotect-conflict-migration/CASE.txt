END-USER FAILURE: KVM dirty/write-protect state permits old guest memory after live migration
EARLIEST WRONG ASSUMPTION:
Dirty logging and write-protection updates do not maintain the invariant that each page is either marked dirty for transfer or protected so any next write will be noticed. A page's post-copy changes escape the final migration bitmap.
CALL / DATA / STATE PATH:
guest network stress -> KVM write-protects guest memory -> competing modifications/bitmap tracking -> migration copies stale page -> destination sees old bytes -> guest/QEMU crashes
ACTUAL REPRODUCTION OR SOURCE-BOUND PLAN:
Original reporter: Intel NON-EPT system; RHEL6 guest with virtio and vhost-net; netperf host→guest while repeatedly migrating. Observed about 1/4 runs. Must disable hardware EPT to recreate exact mode; cannot claim AMD NPT reproduction from Intel report.
FAILURE SIGNAL AND CONTROL:
Destination emits 'guest moved index' / unexpected guest/QEMU crash, or memory checksum mismatch; valid state must be either dirty or protected.
MANUAL INPUT AND QUESTION:
CONSTRUCTED: page copied as 0x11; guest next writes 0x22 without dirty event. Identify destination expected byte and transferred byte, and which invariant could prevent mismatch.
