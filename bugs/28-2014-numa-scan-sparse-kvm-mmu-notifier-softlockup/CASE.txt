END-USER FAILURE: Linux NUMA scan performs expensive KVM MMU invalidations over holes in huge guest memory
EARLIEST WRONG ASSUMPTION:
NUMA balancing walks huge sparse guest mappings and invokes mmu_notifier even where no page is present. KVM pays invalidation work proportional to virtual address span rather than resident pages, causing watchdog soft-lockup latency.
CALL / DATA / STATE PATH:
task_numa_work scans unpopulated VMA -> change_protection / mmu notifier over empty range -> KVM invalidation overhead -> latency/soft lockup; fix narrows invalidation to populated PMD and cond_resched
ACTUAL REPRODUCTION OR SOURCE-BOUND PLAN:
Reporter states warning occurs on very large (>2TiB) KVM VMs. Cannot reproduce exact memory scale on 14GiB machine. Study patch body, create a SMALL demonstrator measuring notifier calls over sparse mmap regions, and explicitly label it a mechanism demonstration, not a reproduction.
FAILURE SIGNAL AND CONTROL:
soft lockup on huge sparse VMs, notifier calls on unmapped ranges; patch moves call to 1GiB PMD and only begins where present page encountered.
MANUAL INPUT AND QUESTION:
PUBLISHED: >2 TiB sparse virtual mapping. CONSTRUCTED: 2 TiB / 1 GiB = 2048 PUD-size windows, whereas 2 TiB / 2 MiB = 1048576 individual PMD-size spans. The 2014 source calls a change_pmd_range() traversal a '1GB area'; do not confuse a PMD table's 1GiB overall coverage with one PMD entry's 2MiB coverage. Derive why notifying on unbacked spans costs CPU even when no pages exist.
