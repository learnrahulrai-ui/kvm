END-USER FAILURE: Prefetch before write-protection leaves a guest page permanently not-present in shadow
EARLIEST WRONG ASSUMPTION:
kvm_mmu_get_page prepopulated a shadow PTE while the guest page-table page was still writable. Guest marked a PTE present afterward; KVM's prefetched notrap entry remained stale and KVM could not intercept the guest update.
CALL / DATA / STATE PATH:
kvm_mmu_get_page -> mmu.prefetch_page -> VCPU1 makes guest PTE present -> rmap_write_protect arrives too late -> guest fault loops without repair
ACTUAL REPRODUCTION OR SOURCE-BOUND PLAN:
Original reproducer is a looping `dmsetup status` in an SMP guest. Build old, pre-patch KVM in an isolated L0 virtual machine capable of nested virtualization, run two guest CPUs, create/activate device-mapper targets on disposable guest storage, and repeat status while capturing fault traces. Compare against a build containing only the patch.
FAILURE SIGNAL AND CONTROL:
Guest hangs/spins in pre-fix report; change order to protect before prefetch and verify it no longer occurs under same workload.
MANUAL INPUT AND QUESTION:
CONSTRUCTED: shadow entry cached nonpresent while current guest PTE becomes present=1. Calculate truth value of entry equality after the guest update. Identify why performing the same operations in opposite order changes visibility.
