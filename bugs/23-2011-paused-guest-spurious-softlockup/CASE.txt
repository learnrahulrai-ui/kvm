END-USER FAILURE: Pausing a KVM guest creates a false soft-lockup diagnosis and breaks naive clock corrections
EARLIEST WRONG ASSUMPTION:
Host stops guest execution, so guest watchdog observes elapsed time without guest progress and incorrectly reports soft lockup. Alternative QEMU saving/restoring TSC per vCPU caused guest wall clock to lag by pause duration.
CALL / DATA / STATE PATH:
host pauses guest -> guest watchdog sees large interval without guest scheduler progress -> false lockup; QEMU resets clock to hide pause -> guest wall clock falls behind
ACTUAL REPRODUCTION OR SOURCE-BOUND PLAN:
Start disposable Linux guest with watchdog, pause QEMU via HMP stop or QMP stop for longer than watchdog threshold, then cont. Compare guest watchdog dmesg/time before/after and a guest with host-pause notification support; do not change host clocksource or use physical host reboot.
FAILURE SIGNAL AND CONTROL:
Guest reports false lockup after being externally paused; inappropriate time compensation produces delayed guest wall clock.
MANUAL INPUT AND QUESTION:
CONSTRUCTED: host stops guest for 45s while vCPU executes 0 guest instructions. Count guest CPU-progress time vs elapsed clock time. Decide which clock a guest watchdog should use for a CPU progress claim.
