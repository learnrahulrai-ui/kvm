B10 | Kernel clocksource watchdog waits on a clock that cannot advance
PUBLIC ORIGIN YEAR: 2026
EVIDENCE STATUS: CONFIRMED_AUTHOR_REPRO_AND_PATCH
CAN TRY ON SECOND LAPTOP: GOOD_ISOLATED_QEMU_GUEST
LOCAL REPRODUCED: NO_REPRO_RUN
CORE FAILURE, NOT AN ERROR-RETURN EXERCISE:
Timeout uses ktime_get_raw_fast_ns backed by jiffies during early boot; boot CPU disables interrupts, which prevent timekeeping clock from advancing, so the timeout itself never expires.
OBSERVED OPERATION THAT MATTERS:
Boot a kernel with clocksource=jiffies and run watchdog skew check under CPU stop with interrupts disabled; use linked public C reproducer.
FUNCTION-TO-FUNCTION REASONING PATH:
CPU0 stop_machine disables IRQ -> CPU1 waits for CPU0 -> CPU0 watchdog waits for CPU1 -> timeout reads frozen jiffies -> loop never exits
ORIGINAL REPORT / PATCH (READ BODY NOT TITLE): https://lkml.iu.edu/2611.0/04403.html
FIX OR UNCERTAINTY: 2026 patch measures wait using clocksource under test, which continues counting with IRQ disabled
REPRODUCTION PROCEDURE AND REQUIRED RESOURCES:
Compile public author source https://github.com/manitofigh/files/blob/main/linux-repros/wdboot.c inside a disposable guest on an affected 7.3 family kernel with clocksource=jiffies and 2 vCPUs. Do not boot your physical laptop with an intentionally broken clocksource.
